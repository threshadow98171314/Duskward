# Duskward 架構規劃

這份文件記錄 Duskward 從原作架構改寫成新架構的方向和順序。世界觀、玩法和美術設計請見[設計文件](DESIGN.md)。

## 為什麼要改

原作的程式在 2014 年前後寫成，現在的狀況是：

| 現況 | 造成的問題 |
|---|---|
| 規則和畫面綁在一起，全靠計時器串接（97 處 `setTimeout`／`setInterval`） | 動畫一改，規則就可能跟著壞；沒辦法加速或跳過動畫 |
| 盤面用字串和正規表示式比對 | 很難加新的方塊規則，也很難測試 |
| 每隻怪物一個類別檔（15 個檔案） | 加一隻怪物要改好幾個地方 |
| 精靈圖座標寫死在 CSS（176 條 `background-position`） | 換一張圖要同時改美術工具、CSS 和程式 |
| 沒有測試、存檔沒有版本號 | 改東西只能靠手動試玩，改存檔格式會毀掉舊存檔 |
| 建築順序自動決定，選項只有休閒模式 | 玩家能做的決定太少 |
| 76 個音效檔在進遊戲前全部載完 | 第一次開啟要等很久 |

## 目標架構

```
src/
  core/      規則：盤面、戰鬥、時間、建造、技能
  content/   資料：資源、建築、怪物、技能、事件
  story/     劇情引擎：章節、條件、對話、選擇、結局
  render/    場景與盤面繪製、特效、動畫佇列
  ui/        狀態列、選單、對話框、教學、設定
  platform/  存檔與版本升級、音效、語系、輸入
tools/art/   美術管線，另外輸出圖集清單
tests/       規則測試、自動對局模擬
```

### 1. 規則核心

- 純粹的規則程式：不碰畫面，也不用計時器。
- 接受指令（交換方塊、施放技能、做出選擇），回傳「發生了哪些事」的清單，畫面層再照清單播放動畫。
- 亂數可以指定種子，同一個種子會得到同一局。
- 帶來的好處：可以不開瀏覽器模擬上千局來檢查平衡，動畫可以加速或跳過，錯誤可以重現。

### 2. 內容資料化

- 怪物、建築、資源、技能和劇情都寫成資料檔，載入時檢查格式。
- 怪物的行為由可重複使用的零件組成：靠近、近戰、遠程、施法、飛行。
- 精靈圖座標由美術工具輸出一份清單，程式和 CSS 都從這份清單產生。

### 3. 選擇系統

- 玩家自己決定下一棟蓋什麼。
- 黃昏抉擇：每天黃昏瑟菈提供三種夜間祝福讓玩家挑一種，效果越強代價越重。
- 技能配置：每晚只能帶兩個暮光技。
- 夜晚導演：依天數、玩家強度和劇情進度決定今晚出現哪些怪物和事件。

### 4. 劇情引擎

- 章節由條件觸發，會記住玩家做過的選擇。
- 多角色對話，附頭像。
- 選擇有後果，例如救下的村民會搬進村子並帶來加成。
- 可以回頭翻閱的守暮日誌和怪物圖鑑。
- 多重結局，例如晨光之心要怎麼處置。
- 世界隨進度改變：太陽一天一天被啃食，村子一盞一盞亮起來。

### 5. 畫面與體驗

- 場景和盤面改用 canvas 繪製，選單和狀態列維持 HTML。
- 提燈光照、粒子、畫面震動、多層遠景。
- 第一天的互動教學、閒置提示、下一棟建築的花費與進度、滑鼠提示。
- 設定：動畫速度、色盲輔助圖樣。
- 手機直式版面，可以安裝成離線應用程式。
- 音樂改成進遊戲後再載入。

### 6. 工程地基

- ES 模組、Vite、TypeScript。
- 單元測試和自動對局模擬。
- 存檔有版本號，格式改變時用升級程式轉換舊存檔。
- 發生錯誤時顯示復原畫面，不讓玩家卡在壞掉的畫面上。
- 測試沒過就不部署。

## 進行順序

每個階段結束時，線上版都必須能正常遊玩。

| 階段 | 內容 | 玩家看得到的改變 | 狀態 |
|---|---|---|---|
| 一、地基 | 換掉建置工具、加入測試、存檔版本號、部署前檢查 | 沒有 | 完成 |
| 二、規則核心 | 把盤面、時間、收穫和戰鬥數值的規則抽出來，畫面照規則回傳的事件播放；錯誤復原畫面 | 幾乎沒有 | 完成 |
| 三、內容資料化 | 怪物、建築等改成資料檔；即時的移動與戰鬥改由規則核心模擬；同時完成怪物改造、墮落晨龍和蝕日者 | 新怪物、新魔王 | 進行中 |
| 四、選擇與劇情 | 建造選擇、黃昏抉擇、劇情引擎、多重結局 | 新玩法、新劇情 | 未開始 |
| 五、畫面與體驗 | canvas、光影特效、教學、提示、手機版面 | 新畫面 | 未開始 |
| 六、重玩價值 | 二周目的規則變化、成就、每日種子 | 新模式 | 未開始 |

選擇系統加入後，原本的數值平衡需要重新調整。舊存檔會保留，由升級程式轉換。

## 第一階段：地基

這個階段不改遊戲行為，只換掉底下的工具。

### 檔案配置

| 路徑 | 內容 |
|---|---|
| `index.html` | 遊戲頁面，Vite 的進入點 |
| `src/` | 遊戲程式（ES 模組） |
| `src/platform/` | 新寫的平台層模組，第一個是存檔版本與升級 |
| `src/vendor/` | 沿用的第三方程式：jQuery 2.0.3 和 Base64 |
| `public/` | 原樣複製的靜態檔案：圖片、音效、CSS |
| `tests/` | 測試 |
| `tools/art/legacy/` | 原作的美術原始檔，不會出現在發布版裡 |
| `dist/` | 建置輸出，不放進版本庫 |

### 這個階段的取捨

- **既有模組先轉成 ES 模組的 JavaScript，還不是 TypeScript。** 新寫的模組和測試用 TypeScript；既有模組會在第二階段之後逐一重寫時改成 TypeScript。
- **jQuery 先留著。** 畫面層在第五階段改寫時才會拿掉。
- **CSS 先放在 `public/` 原樣提供。** 程式會用固定網址預先載入精靈圖，CSS 如果交給建置工具處理，圖片會被改名而重複下載。
- **錯誤復原畫面延後。** 它需要規則和畫面分開之後才做得乾淨，排在第二階段。
- **少數參照改成用到時才查找。** RequireJS 允許模組在函式裡用 `require()` 呼叫彼此。這些呼叫如果全部改成 import，會形成循環，子類別可能比基底類別先執行（例如 `Block.prototype = new WorldEntity()` 時 `WorldEntity` 還沒載入）。其中 8 組參照，例如 Entity 透過 Graphics 繪圖、盤面回頭詢問 Engine 現在是不是夜晚，改由 `src/app/modules.js` 在執行時查找。測試會檢查不再出現這種循環。它們來自實體透過 Graphics 繪圖、模組回頭呼叫 Engine，要等第三階段重寫即時的世界、第五階段重寫畫面後才會消失。

### 轉換時發現的問題

- 原作有不少沒宣告的變數，在寬鬆模式下會變成全域變數；ES 模組一律是嚴格模式，這些地方會直接拋錯，已全部補上宣告。內附的 Base64 函式庫也有同樣的問題，導致匯入代碼完全讀不進來，一併修正。
- 存檔欄位的內容是 `null` 時，標題畫面會出錯；匯入無效的代碼會把內容寫壞。存檔加上版本號後，這兩種情況都改成當成空欄位，匯入時也會先檢查。
- 戰利品的抽選把字串索引直接加 1（`"1" + 1` 會變成 `"11"`）。目前每個戰利品池都只有一種道具，所以沒有影響；但池子放到三種以上時，第三種之後就抽不到。留到內容資料化時一起修。

### 存檔版本

- 存檔加上 `version` 欄位。沒有這個欄位的存檔視為第 0 版。
- 讀取存檔時，依序套用每一版的升級程式，直到目前的版本。
- 存檔內容壞掉時當成空欄位處理，不讓遊戲當掉。
- 匯入存檔代碼前先檢查內容，確認是有效的存檔才寫入。

### 檢查與部署（第一階段）

每次推送到 `main` 時依序執行，任何一步失敗就不部署：

1. 型別檢查（`npm run typecheck`）
2. 程式檢查（`npm run lint`）
3. 測試（`npm test`）
4. 建置（`npm run build`）
5. 把 `dist/` 發布到 GitHub Pages

## 第二階段：規則核心

### 範圍

讀過程式後，「規則」其實分成兩種：

| 種類 | 例子 | 原本寫在哪裡 | 處理方式 |
|---|---|---|---|
| 一步一步的規則 | 交換與消除、連鎖、補方塊、時間推進、黃昏與日夜交替、消除後的效果、飢餓、能蓋哪些建築、經驗與升級、傷害公式 | 盤面和世界模組的函式 | 這個階段抽出來 |
| 即時的移動與戰鬥 | 主角走去搬資源和蓋房子、怪物靠近和出手的時機、投射物 | 每種怪物和行動的類別，靠動畫影格和畫面上量出來的寬度推進 | 移到第三階段 |

即時的部分要抽出來，等於重寫整個怪物與行動系統。第三階段本來就要把怪物改成用零件（靠近、近戰、遠程、施法、飛行）組成的資料，兩件事一起做，這套系統只需要重寫一次。

### 新的模組

規則核心放在 `src/core/`，用 TypeScript 撰寫：

| 模組 | 內容 |
|---|---|
| `random.ts` | 可以指定種子的亂數，同一個種子會得到同一串亂數 |
| `board.ts` | 盤面：交換、找出消除、連鎖、燈籠與日輪方塊、暮晶、影縛和爆炸、補充方塊、判斷還有沒有步可走 |
| `day.ts` | 時間：每一步推進多少、黃昏、日夜交替 |
| `harvest.ts` | 消除後的效果：白天收集資源（含建築加成）、夜晚生出怪物或補充盾牌與劍、黃昏累積結界 |
| `progress.ts` | 建築是否可蓋、經驗與升級 |
| `combat.ts` | 傷害公式：主角的攻擊力；受傷時結界和盾牌先吸收、凍結時減半；怪物的血量和攻擊力 |

規則核心的模組：

- 不碰畫面、不用計時器、不讀全域狀態，需要的資料由呼叫端傳進來
- 要用亂數時，由呼叫端傳入亂數產生器
- 回傳「發生了哪些事」，原本的模組再依結果觸發事件、播放動畫

### 盤面一波一波地結算

一次交換可能引發好幾波消除。原作每一波都等畫面的動畫播完，才結算下一波，而世界會在每一波之間反應，例如夜晚每一波都可能生出怪物。所以規則核心也一次結算一波：畫面播完這一波，再請核心結算下一波，玩家看到的節奏和原本一樣。

### 錯誤復原

遊戲執行中出現沒有攔到的錯誤時，顯示一個復原畫面：說明發生了問題、存檔停在最近一次天亮時的進度，並提供重新載入的按鈕和可以複製的錯誤內容，方便回報。

### 模擬

規則核心不需要瀏覽器，所以測試可以用固定的種子大量模擬盤面，檢查連鎖、收穫和「沒有步可走」出現的頻率，數值調整後也能立刻看出影響。

### 結果

| 模組 | 用到它的原有模組 |
|---|---|
| `random.ts` | 盤面（填盤、補方塊、隨機放置特效） |
| `board.ts` | `gameboard.js` 改寫成轉接層：狀態和規則交給核心，自己只把結果翻譯成原本的事件和繪圖請求 |
| `day.ts`、`harvest.ts` | `world.js` 的時鐘和消除後的效果 |
| `progress.ts` | `world.js` 的建築解鎖、`dude.js` 的經驗與升級、`gamestate.js` 的生命上限 |
| `combat.ts` | `dude.js` 的攻擊與受傷、怪物的數值、`gamestate.js` 的劍與盾上限、`world.js` 的二周目倍率 |
| `simulate.ts` | 測試 |

另外新增 `src/ui/crash.ts`（錯誤復原畫面）。

- **盤面和原作完全一致。**（第二階段完成時如此；之後刻意調整了第 4 波起的補方塊，見「開局連鎖的調整」。） 換掉之前，用比對測試讓原作的盤面模組和規則核心從同一個盤面、同一串亂數出發，隨機下了 60 局（1000 多步、300 多波消除，包含各種特效），每一波的結果都相同。這個測試留下來，改成檢查新的盤面模組是否照原作的順序觸發事件。
- **唯一刻意的差異是「還有沒有步可走」。** 原作的檢查會漏看某些可走的步，誤判時會重洗盤面並給懲罰；也沒有排除被影縛的方塊，只剩被綁住的方塊能走時玩家會卡住。新的判斷逐一嘗試每一組交換。
- **即時的移動與戰鬥還在原本的類別裡**，第三階段處理。自動測試涵蓋了規則本身，但沒有涵蓋主角和怪物在畫面上的移動與出手時機，這部分靠在瀏覽器實際遊玩檢查。

### 模擬發現的平衡問題

`tests/__snapshots__/simulation.test.ts.snap` 記錄四個村莊階段各模擬 2000 步的統計：

| 方塊種類 | 連鎖中位數 | 一成的步超過 | 最長連鎖 | 每步收穫 |
|---|---|---|---|---|
| 3 種（遊戲剛開始） | 9 波 | 69 波 | 310 波 | 707 塊 |
| 4 種（蓋好磚窯） | 2 波 | 7 波 | 28 波 | 27 塊 |
| 5 種（蓋好織坊） | 1 波 | 4 波 | 11 波 | 9.5 塊 |
| 6 種（蓋好燈塔） | 1 波 | 3 波 | 7 波 | 6.4 塊 |

只有三種方塊時，補進來的方塊很容易立刻連成一線，燈籠又會清掉整行整列，連鎖一發不可收拾：一次交換最多連續消除了三百多波，每步的收穫是蓋好燈塔後的一百倍以上。原作就是如此。第二階段本身不改行為，之後的調整見下一節。

### 開局連鎖的調整

第二階段完成後，依模擬結果做了三項調整：

1. **長連鎖會逐漸收斂。** 一步的第 4 波起，補進來的方塊和周圍連成一線的機率逐波降低（第 4 波少 25%，第 5 波少 50%，第 6 波少 75%），第 7 波起只要有別的種類可選，就不會直接連線。前三波和原作完全相同，一般的小連鎖手感不變。（`board.ts`）
2. **長連鎖的動畫會加速，也能快轉。** 每波動畫原本 400 毫秒，第 4 波起 300、第 7 波起 200、第 13 波起 100 毫秒。連鎖進行中點一下盤面，剩下的波數用最快的速度播完。第一次連鎖到 6 波時，瑟菈的日誌會提示可以快轉。（`graphics/gameboard.js`、`gameboard.js`、`engine.js`）
3. **豐收加成。** 白天一步之內收齊四種以上的資源（暮晶不算），這一步收到的每種資源再多給一部分：四種多 50%，五種多 100%，六種多 150%，同樣乘上建築的倍率。只有三種方塊時不會觸發，所以只補後期。（`harvest.ts`、`world.js`）

調整後的模擬（各 2000 步，豐收以每一步都在白天計算）：

| 方塊種類 | 連鎖中位數 | 一成的步超過 | 最長連鎖 | 每步收穫 | 豐收加成 | 合計 | 原作 |
|---|---|---|---|---|---|---|---|
| 3 種 | 5 波 | 11 波 | 24 波 | 82 塊 | — | 82 塊 | 707 塊 |
| 4 種 | 2 波 | 6 波 | 17 波 | 20 塊 | 7.8 塊 | 28 塊 | 27 塊 |
| 5 種 | 1 波 | 3 波 | 8 波 | 8.7 塊 | 4.1 塊 | 12.8 塊 | 9.5 塊 |
| 6 種 | 1 波 | 3 波 | 9 波 | 6.3 塊 | 2.9 塊 | 9.2 塊 | 6.4 塊 |

開局和蓋好磚窯後的落差從 26 倍縮小到約 3 倍，蓋好磚窯後的收穫和原作差不多，五、六種方塊時比原作多約四成。實際玩一局新遊戲，第一天的 20 步內就蓋好了小屋和磚窯。資源倉庫有容量上限（小屋時 9 格、每格 30），原作開局一步的收穫平均就超過整個倉庫的容量，多出來的會把最舊的格子擠掉，所以那些收穫大多本來就留不住。

## 第三階段：內容資料化

### 分步

每一步都能玩，也都會部署。

| 步驟 | 內容 | 狀態 |
|---|---|---|
| 1 | 資源、建築、道具、法術、暮光技和持續效果改成 `src/content/` 的資料檔，載入時檢查 | 完成 |
| 2 | 主角與怪物的即時移動和戰鬥改由規則核心模擬；怪物的行為由零件組成，數值寫在資料檔 | 未開始 |

### 第 1 步：內容資料

| 檔案 | 內容 |
|---|---|
| `types.ts` | 各種資料的形狀 |
| `resources.ts` | 資源方塊：代號、夜晚效果、對龍的效果、建築倍率 |
| `buildings.ts` | 建築：位置、花費、解鎖條件、升級關係、蓋好後的效果 |
| `items.ts` | 寶箱裡的道具、稀有度和寶物池 |
| `magic.ts` | 法術、暮光技和持續效果 |
| `monsters.ts` | 目前只有怪物名單，第 2 步補上數值和行為 |
| `validate.ts`、`index.ts` | 檢查內容，並把全部內容集中起來 |

- 原本寫成函式的內容改成資料描述。道具、法術和暮光技的效果是一串效果（`heal`、`damageAll`、`stateEffect` 等），白天和晚上不同的就分成 `day`、`night` 兩串，實際執行寫在 `src/app/effects.js`。建築蓋好後的效果（倉庫變大、開啟魔法等）寫成 `onBuilt`。暮光塔原本用函式檢查碎片數量，改成 `requiredGems: 4`。
- 遊戲載入時，`gamecontent.js` 先檢查全部內容：名稱重複、引用不存在的資源、建築、怪物、道具或持續效果、數字超出範圍、夜晚效果的順序（`default` 要放最後）、升級關係繞成一圈。只要有問題就停下並列出全部問題，畫面會顯示錯誤復原畫面。
- 修正原作寶物池的錯誤：原作把陣列索引當字串相加（`"1" + 1` 會變成 `"11"`），寶物池超過兩種道具時，第二種被抽中的機率會偏高，最後一種永遠抽不到。目前每個寶物池只有一種道具，所以還沒有影響，但之後加入新道具時就會出問題。
