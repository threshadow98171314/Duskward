# Duskward 架構規劃

這份文件記錄 Duskward 從原作架構改寫成新架構的方向和順序。世界觀、玩法和美術設計請見[設計文件](DESIGN.md)。

## 為什麼要改

原作的程式在 2014 年前後寫成，現在的狀況是：

| 現況 | 造成的問題 |
|---|---|
| 規則和畫面綁在一起，全靠計時器串接（97 處 `setTimeout`／`setInterval`） | 動畫一改，規則就可能跟著壞；沒辦法加速或跳過動畫 |
| 盤面用字串和正規表示式比對 | 很難加新的方塊規則，也很難測試 |
| 每隻怪物一個類別檔（15 個檔案） | 加一隻怪物要改好幾個地方 |
| 精靈圖座標寫死在 CSS（176 條 `background-position`） | 換一張圖要同時改美術工具、CSS 和程式 |
| 沒有測試、存檔沒有版本號 | 改東西只能靠手動試玩，改存檔格式會毀掉舊存檔 |
| 建築順序自動決定，選項只有休閒模式 | 玩家能做的決定太少 |
| 76 個音效檔在進遊戲前全部載完 | 第一次開啟要等很久 |

## 目標架構

```
src/
  core/      規則：盤面、戰鬥、時間、建造、技能
  content/   資料：資源、建築、怪物、技能、事件
  story/     劇情引擎：章節、條件、對話、選擇、結局
  render/    場景與盤面繪製、特效、動畫佇列
  ui/        狀態列、選單、對話框、教學、設定
  platform/  存檔與版本升級、音效、語系、輸入
tools/art/   美術管線，另外輸出圖集清單
tests/       規則測試、自動對局模擬
```

### 1. 規則核心

- 純粹的規則程式：不碰畫面，也不用計時器。
- 接受指令（交換方塊、施放技能、做出選擇），回傳「發生了哪些事」的清單，畫面層再照清單播放動畫。
- 亂數可以指定種子，同一個種子會得到同一局。
- 帶來的好處：可以不開瀏覽器模擬上千局來檢查平衡，動畫可以加速或跳過，錯誤可以重現。

### 2. 內容資料化

- 怪物、建築、資源、技能和劇情都寫成資料檔，載入時檢查格式。
- 怪物的行為由可重複使用的零件組成：靠近、近戰、遠程、施法、飛行。
- 精靈圖座標由美術工具輸出一份清單，程式和 CSS 都從這份清單產生。

### 3. 選擇系統

- 玩家自己決定下一棟蓋什麼。
- 黃昏抉擇：每天黃昏瑟菈提供三種夜間祝福讓玩家挑一種，效果越強代價越重。
- 技能配置：每晚只能帶兩個暮光技。
- 夜晚導演：依天數、玩家強度和劇情進度決定今晚出現哪些怪物和事件。

### 4. 劇情引擎

- 章節由條件觸發，會記住玩家做過的選擇。
- 多角色對話，附頭像。
- 選擇有後果，例如救下的村民會搬進村子並帶來加成。
- 可以回頭翻閱的守暮日誌和怪物圖鑑。
- 多重結局，例如晨光之心要怎麼處置。
- 世界隨進度改變：太陽一天一天被啃食，村子一盞一盞亮起來。

### 5. 畫面與體驗

- 場景和盤面改用 canvas 繪製，選單和狀態列維持 HTML。
- 提燈光照、粒子、畫面震動、多層遠景。
- 第一天的互動教學、閒置提示、下一棟建築的花費與進度、滑鼠提示。
- 設定：動畫速度、色盲輔助圖樣。
- 手機直式版面，可以安裝成離線應用程式。
- 音樂改成進遊戲後再載入。

### 6. 工程地基

- ES 模組、Vite、TypeScript。
- 單元測試和自動對局模擬。
- 存檔有版本號，格式改變時用升級程式轉換舊存檔。
- 發生錯誤時顯示復原畫面，不讓玩家卡在壞掉的畫面上。
- 測試沒過就不部署。

## 進行順序

每個階段結束時，線上版都必須能正常遊玩。

| 階段 | 內容 | 玩家看得到的改變 | 狀態 |
|---|---|---|---|
| 一、地基 | 換掉建置工具、加入測試、存檔版本號、部署前檢查 | 沒有 | 完成 |
| 二、規則核心 | 把盤面、時間、收穫和戰鬥數值的規則抽出來，畫面照規則回傳的事件播放；錯誤復原畫面 | 幾乎沒有 | 完成 |
| 三、內容資料化 | 怪物、建築等改成資料檔；即時的移動與戰鬥改由規則核心模擬；同時完成怪物改造、墮落晨龍和蝕日者 | 新怪物、新魔王 | 完成 |
| 四、選擇與劇情 | 建造選擇、黃昏抉擇、劇情引擎、多重結局 | 新玩法、新劇情 | 完成 |
| 五、畫面與體驗 | canvas、光影特效、教學、提示、手機版面 | 新畫面 | 進行中 |
| 六、重玩價值 | 二周目的規則變化、成就、每日種子 | 新模式 | 未開始 |

選擇系統加入後，原本的數值平衡需要重新調整。舊存檔會保留，由升級程式轉換。

## 第一階段：地基

這個階段不改遊戲行為，只換掉底下的工具。

### 檔案配置

| 路徑 | 內容 |
|---|---|
| `index.html` | 遊戲頁面，Vite 的進入點 |
| `src/` | 遊戲程式（ES 模組） |
| `src/platform/` | 新寫的平台層模組，第一個是存檔版本與升級 |
| `src/vendor/` | 沿用的第三方程式：jQuery 2.0.3 和 Base64 |
| `public/` | 原樣複製的靜態檔案：圖片、音效、CSS |
| `tests/` | 測試 |
| `tools/art/legacy/` | 原作的美術原始檔，不會出現在發布版裡 |
| `dist/` | 建置輸出，不放進版本庫 |

### 這個階段的取捨

- **既有模組先轉成 ES 模組的 JavaScript，還不是 TypeScript。** 新寫的模組和測試用 TypeScript；既有模組會在第二階段之後逐一重寫時改成 TypeScript。
- **jQuery 先留著。** 畫面層在第五階段改寫時才會拿掉。
- **CSS 先放在 `public/` 原樣提供。** 程式會用固定網址預先載入精靈圖，CSS 如果交給建置工具處理，圖片會被改名而重複下載。
- **錯誤復原畫面延後。** 它需要規則和畫面分開之後才做得乾淨，排在第二階段。
- **少數參照改成用到時才查找。** RequireJS 允許模組在函式裡用 `require()` 呼叫彼此。這些呼叫如果全部改成 import，會形成循環，子類別可能比基底類別先執行（例如 `Block.prototype = new WorldEntity()` 時 `WorldEntity` 還沒載入）。其中 8 組參照，例如 Entity 透過 Graphics 繪圖、盤面回頭詢問 Engine 現在是不是夜晚，改由 `src/app/modules.js` 在執行時查找。測試會檢查不再出現這種循環。它們來自實體透過 Graphics 繪圖、模組回頭呼叫 Engine，要等第三階段重寫即時的世界、第五階段重寫畫面後才會消失。（第三階段第 2 步之後剩 7 組：怪物的動作改由規則核心模擬後，WorldEntity 不再需要查找動作工廠。）

### 轉換時發現的問題

- 原作有不少沒宣告的變數，在寬鬆模式下會變成全域變數；ES 模組一律是嚴格模式，這些地方會直接拋錯，已全部補上宣告。內附的 Base64 函式庫也有同樣的問題，導致匯入代碼完全讀不進來，一併修正。
- 存檔欄位的內容是 `null` 時，標題畫面會出錯；匯入無效的代碼會把內容寫壞。存檔加上版本號後，這兩種情況都改成當成空欄位，匯入時也會先檢查。
- 戰利品的抽選把字串索引直接加 1（`"1" + 1` 會變成 `"11"`）。目前每個戰利品池都只有一種道具，所以沒有影響；但池子放到三種以上時，第三種之後就抽不到。留到內容資料化時一起修。

### 存檔版本

- 存檔加上 `version` 欄位。沒有這個欄位的存檔視為第 0 版。
- 讀取存檔時，依序套用每一版的升級程式，直到目前的版本。
- 存檔內容壞掉時當成空欄位處理，不讓遊戲當掉。
- 匯入存檔代碼前先檢查內容，確認是有效的存檔才寫入。

### 檢查與部署（第一階段）

每次推送到 `main` 時依序執行，任何一步失敗就不部署：

1. 型別檢查（`npm run typecheck`）
2. 程式檢查（`npm run lint`）
3. 測試（`npm test`）
4. 建置（`npm run build`）
5. 把 `dist/` 發布到 GitHub Pages

## 第二階段：規則核心

### 範圍

讀過程式後，「規則」其實分成兩種：

| 種類 | 例子 | 原本寫在哪裡 | 處理方式 |
|---|---|---|---|
| 一步一步的規則 | 交換與消除、連鎖、補方塊、時間推進、黃昏與日夜交替、消除後的效果、飢餓、能蓋哪些建築、經驗與升級、傷害公式 | 盤面和世界模組的函式 | 這個階段抽出來 |
| 即時的移動與戰鬥 | 主角走去搬資源和蓋房子、怪物靠近和出手的時機、投射物 | 每種怪物和行動的類別，靠動畫影格和畫面上量出來的寬度推進 | 移到第三階段 |

即時的部分要抽出來，等於重寫整個怪物與行動系統。第三階段本來就要把怪物改成用零件（靠近、近戰、遠程、施法、飛行）組成的資料，兩件事一起做，這套系統只需要重寫一次。

### 新的模組

規則核心放在 `src/core/`，用 TypeScript 撰寫：

| 模組 | 內容 |
|---|---|
| `random.ts` | 可以指定種子的亂數，同一個種子會得到同一串亂數 |
| `board.ts` | 盤面：交換、找出消除、連鎖、燈籠與日輪方塊、暮晶、影縛和爆炸、補充方塊、判斷還有沒有步可走 |
| `day.ts` | 時間：每一步推進多少、黃昏、日夜交替 |
| `harvest.ts` | 消除後的效果：白天收集資源（含建築加成）、夜晚生出怪物或補充盾牌與劍、黃昏累積結界 |
| `progress.ts` | 建築是否可蓋、經驗與升級 |
| `combat.ts` | 傷害公式：主角的攻擊力；受傷時結界和盾牌先吸收、凍結時減半；怪物的血量和攻擊力 |

規則核心的模組：

- 不碰畫面、不用計時器、不讀全域狀態，需要的資料由呼叫端傳進來
- 要用亂數時，由呼叫端傳入亂數產生器
- 回傳「發生了哪些事」，原本的模組再依結果觸發事件、播放動畫

### 盤面一波一波地結算

一次交換可能引發好幾波消除。原作每一波都等畫面的動畫播完，才結算下一波，而世界會在每一波之間反應，例如夜晚每一波都可能生出怪物。所以規則核心也一次結算一波：畫面播完這一波，再請核心結算下一波，玩家看到的節奏和原本一樣。

### 錯誤復原

遊戲執行中出現沒有攔到的錯誤時，顯示一個復原畫面：說明發生了問題、存檔停在最近一次天亮時的進度，並提供重新載入的按鈕和可以複製的錯誤內容，方便回報。

### 模擬

規則核心不需要瀏覽器，所以測試可以用固定的種子大量模擬盤面，檢查連鎖、收穫和「沒有步可走」出現的頻率，數值調整後也能立刻看出影響。

### 結果

| 模組 | 用到它的原有模組 |
|---|---|
| `random.ts` | 盤面（填盤、補方塊、隨機放置特效） |
| `board.ts` | `gameboard.js` 改寫成轉接層：狀態和規則交給核心，自己只把結果翻譯成原本的事件和繪圖請求 |
| `day.ts`、`harvest.ts` | `world.js` 的時鐘和消除後的效果 |
| `progress.ts` | `world.js` 的建築解鎖、`dude.js` 的經驗與升級、`gamestate.js` 的生命上限 |
| `combat.ts` | `dude.js` 的攻擊與受傷、怪物的數值、`gamestate.js` 的劍與盾上限、`world.js` 的二周目倍率 |
| `simulate.ts` | 測試 |

另外新增 `src/ui/crash.ts`（錯誤復原畫面）。

- **盤面和原作完全一致。**（第二階段完成時如此；之後刻意調整了第 4 波起的補方塊，見「開局連鎖的調整」。） 換掉之前，用比對測試讓原作的盤面模組和規則核心從同一個盤面、同一串亂數出發，隨機下了 60 局（1000 多步、300 多波消除，包含各種特效），每一波的結果都相同。這個測試留下來，改成檢查新的盤面模組是否照原作的順序觸發事件。
- **唯一刻意的差異是「還有沒有步可走」。** 原作的檢查會漏看某些可走的步，誤判時會重洗盤面並給懲罰；也沒有排除被影縛的方塊，只剩被綁住的方塊能走時玩家會卡住。新的判斷逐一嘗試每一組交換。
- **即時的移動與戰鬥還在原本的類別裡**，第三階段處理。自動測試涵蓋了規則本身，但沒有涵蓋主角和怪物在畫面上的移動與出手時機，這部分靠在瀏覽器實際遊玩檢查。

### 模擬發現的平衡問題

`tests/__snapshots__/simulation.test.ts.snap` 記錄四個村莊階段各模擬 2000 步的統計：

| 方塊種類 | 連鎖中位數 | 一成的步超過 | 最長連鎖 | 每步收穫 |
|---|---|---|---|---|
| 3 種（遊戲剛開始） | 9 波 | 69 波 | 310 波 | 707 塊 |
| 4 種（蓋好磚窯） | 2 波 | 7 波 | 28 波 | 27 塊 |
| 5 種（蓋好織坊） | 1 波 | 4 波 | 11 波 | 9.5 塊 |
| 6 種（蓋好燈塔） | 1 波 | 3 波 | 7 波 | 6.4 塊 |

只有三種方塊時，補進來的方塊很容易立刻連成一線，燈籠又會清掉整行整列，連鎖一發不可收拾：一次交換最多連續消除了三百多波，每步的收穫是蓋好燈塔後的一百倍以上。原作就是如此。第二階段本身不改行為，之後的調整見下一節。

### 開局連鎖的調整

第二階段完成後，依模擬結果做了三項調整：

1. **長連鎖會逐漸收斂。** 一步的第 4 波起，補進來的方塊和周圍連成一線的機率逐波降低（第 4 波少 25%，第 5 波少 50%，第 6 波少 75%），第 7 波起只要有別的種類可選，就不會直接連線。前三波和原作完全相同，一般的小連鎖手感不變。（`board.ts`）
2. **長連鎖的動畫會加速，也能快轉。** 每波動畫原本 400 毫秒，第 4 波起 300、第 7 波起 200、第 13 波起 100 毫秒。連鎖進行中點一下盤面，剩下的波數用最快的速度播完。第一次連鎖到 6 波時，瑟菈的日誌會提示可以快轉。（`graphics/gameboard.js`、`gameboard.js`、`engine.js`）
3. **豐收加成。** 白天一步之內收齊四種以上的資源（暮晶不算），這一步收到的每種資源再多給一部分：四種多 50%，五種多 100%，六種多 150%，同樣乘上建築的倍率。只有三種方塊時不會觸發，所以只補後期。（`harvest.ts`、`world.js`）

調整後的模擬（各 2000 步，豐收以每一步都在白天計算）：

| 方塊種類 | 連鎖中位數 | 一成的步超過 | 最長連鎖 | 每步收穫 | 豐收加成 | 合計 | 原作 |
|---|---|---|---|---|---|---|---|
| 3 種 | 5 波 | 11 波 | 24 波 | 82 塊 | — | 82 塊 | 707 塊 |
| 4 種 | 2 波 | 6 波 | 17 波 | 20 塊 | 7.8 塊 | 28 塊 | 27 塊 |
| 5 種 | 1 波 | 3 波 | 8 波 | 8.7 塊 | 4.1 塊 | 12.8 塊 | 9.5 塊 |
| 6 種 | 1 波 | 3 波 | 9 波 | 6.3 塊 | 2.9 塊 | 9.2 塊 | 6.4 塊 |

開局和蓋好磚窯後的落差從 26 倍縮小到約 3 倍，蓋好磚窯後的收穫和原作差不多，五、六種方塊時比原作多約四成。實際玩一局新遊戲，第一天的 20 步內就蓋好了小屋和磚窯。資源倉庫有容量上限（小屋時 9 格、每格 30），原作開局一步的收穫平均就超過整個倉庫的容量，多出來的會把最舊的格子擠掉，所以那些收穫大多本來就留不住。

## 第三階段：內容資料化

### 分步

每一步都能玩，也都會部署。

| 步驟 | 內容 | 狀態 |
|---|---|---|
| 1 | 資源、建築、道具、法術、暮光技和持續效果改成 `src/content/` 的資料檔，載入時檢查 | 完成 |
| 2 | 主角與怪物的即時移動和戰鬥改由規則核心模擬；怪物的行為由零件組成，數值寫在資料檔 | 完成 |
| 3 | 怪物依對照表改名、重畫，加入影魅、燈蛾、暮鴉 | 完成 |
| 4 | 墮落晨龍：移進模擬、重畫，擊敗後掉落晨光之心 | 完成 |

| 檔案 | 內容 |

| `types.ts` | 各種資料的形狀 |

- 原本寫成函式的內容改成資料描述。道具、法術和暮光技的效果是一串效果（`heal`、`damageAll`、`stateEffect` 等），白天和晚上不同的就分成 `day`、`night` 兩串，實際執行寫在 `src/app/effects.js`。建築蓋好後的效果（倉庫變大、開啟魔法等）寫成 `onBuilt`。暮光塔原本用函式檢查碎片數量，改成 `requiredGems: 4`。
- 遊戲載入時，`gamecontent.js` 先檢查全部內容：名稱重複、引用不存在的資源、建築、怪物、道具或持續效果、數字超出範圍、夜晚效果的順序（`default` 要放最後）、升級關係繞成一圈。只要有問題就停下並列出全部問題，畫面會顯示錯誤復原畫面。
- 修正原作寶物池的錯誤：原作把陣列索引當字串相加（`"1" + 1` 會變成 `"11"`），寶物池超過兩種道具時，第二種被抽中的機率會偏高，最後一種永遠抽不到。目前每個寶物池只有一種道具，所以還沒有影響，但之後加入新道具時就會出問題。

### 第 2 步：戰場模擬

`src/core/field.ts` 模擬村子前面這條路：主角、怪物、寶箱和飛行中的箭在哪裡、正在做什麼。時間以 100 毫秒為一格推進，每個角色每格都會移動一點，每兩格（主角加速時每格）走一步動畫，決定接下來做什麼，或播放手上動作的下一格。攻擊在固定的動畫格命中，時機和原作相同：一般攻擊每 4 步一次、第 2 步命中；連擊在第 2 和第 4 步各打一下；射手在第 4 步放箭，箭飛 1 秒，落點離主角超過 5 像素就落空；長夜祭司依自己的計時施法和瞬移。

- **怪物是資料。** 數值、大小和行為零件（近戰、連擊、遠程、施法、瞬移）寫在 `src/content/monsters.ts`，載入時一併檢查。13 個幾乎一樣的怪物類別和 12 個動作類別刪除，畫面上只剩一個通用的 `FieldMonster`。
- **主角也在戰場上。** 晚上找最近的敵人、追上去打，清完後去開寶箱；白天的搬運和蓋房也由模擬執行，但搬哪一塊、蓋哪一棟仍由世界模組決定（`World.nextTask`）。主角的生命、盾和劍屬於遊戲狀態，模擬透過 `FieldHost` 詢問「這一擊多重」「主角受傷了」。
- **畫面照模擬播放。** `src/app/fieldview.js` 每格把角色移到模擬的位置、換成對應的動作與影格；兩格之間平滑移動。分頁在背景、畫面沒有繪製時，下一格會直接跳到正確的位置，不會越落越遠。
- **龍暫時是外部角色。** 第 4 步改寫之前，龍仍由原本的類別自己運作，以 `Outsider` 的形式接上戰場，主角會去打牠；振翅把主角擊退改成呼叫戰場。
- **測試。** 戰場有 19 個單元測試（攻擊時機、命中與落空、施法和瞬移、找最近的敵人、開寶箱、搬運、蓋房、被打斷、加速、時間凍結、清場、擊退、天亮），同一場戰鬥每次結果都一樣。另外 `simulation.test.ts` 多了一份單挑報表：每種怪物對上大約會遇到牠的主角等級與裝備，記錄要打多久、主角掉多少血。

刻意和原作不同的地方：

- 時間凍結（暮光技「時之燈」和法術）現在讓正在走路的怪物也停下來。原作只是不讓怪物開始下一個動作，已經在走的會一路走完。
- 被龍的冰凍住的主角完全不能動。原作在走路途中被凍住，還會滑完那段路。
- 主角追擊時一路跟著目標最新的位置；原作是出發時瞄準一次，每 4 步再重新瞄準。
- 加速、凍結等效果開始時，原作會把主角手上的動作重新開始一次，蓋到一半的建築會從頭蓋；現在會接著做。
- 升級或炸彈清場時，每隻怪物只判定一次掉寶；原作升級清場時會判定兩次。

已在瀏覽器實際玩過：主角爬進場、蓋小屋、搬運、蓋磚窯、入夜打怪、開寶箱、天亮開箱、被圍攻倒下後從存檔重來、升級清場、加速法術、射手放箭、長夜祭司施法和瞬移、召喚龍並與牠交戰。

### 第 3 步：怪物改造與新怪物

- **重繪。** 原作的怪物是白色剪影。`tools/art/monsters.py` 保留原本的動畫，依每個像素在剪影裡的深度重新上色：邊緣是輪廓光，內部由上往下漸暗，外圍加深色描邊，每種怪物一組配色。新怪物（影魅、燈蛾、暮鴉）先畫成剪影的動畫，再用同樣的方式上色，接在 `monsters.png` 原本的怪物後面。
- **名稱和初見日誌。** 每種怪物都有中英文名稱（`MONSTER_NAMES`），第一次出現時瑟菈會在日誌裡介紹牠。測試會檢查每種怪物都有名稱和日誌。
- **新的出現方式。** 除了消除方塊叫出怪物，資源可以「吸引」怪物（燈火吸引燈蛾，`attracts`），另外還有不靠方塊的「召喚」：連鎖到第幾波、入夜時成群出現（`CALLS`，計算寫在 `src/core/night.ts`）。這兩種都是資料，載入時檢查，第四階段的夜晚導演會在這個基礎上擴充。
- **新的零件。** 怪物可以飛（畫在空中），也可以有自己的「獵物」：燈蛾的攻擊先啃結界（`prey: 'ward'`，每口吃掉兩倍傷害）。影魅用既有的施法零件施放影縛。
- 單挑報表加上三種新怪物。設計的細節請見[設計文件](DESIGN.md)的「新怪物」。

### 第 4 步：墮落晨龍

- **魔王也在戰場上。** `field.ts` 加入魔王：先降落（這段時間打不到牠），之後依出招表一招接一招。沒有待發的招式時，主角靠近就咬、離遠就吐火球；主角消除的方塊會觸發其他招式（麥穗是振翅、陶土是冰息、布匹是烈焰），排隊等著出。每一招都寫成資料（`src/content/bosses.ts`）：多久命中、多久結束、傷害、要多近才打得到、是否凍結主角、把主角吹開多遠、在地上留下多久的火、是否吹熄火焰。時間和原作的動畫一致。龍的硬皮會吸收每一擊的 2 點傷害。
- **龍只負責畫面。** `dragon.js` 只剩身體、脖子和頭的姿勢，以及每招的特效（火球、冰息、烈焰、振翅、倒下時的掙扎和爆炸），由戰場的事件驅動。原本 7 個龍的動作類別和整個 `action/` 目錄刪除，`WorldEntity` 也不再需要舊的移動方法，晚綁定的參照又少一組。
- **打倒龍不再結束遊戲。** 龍倒下後掉出「晨光之心」，主角撿起後放在大道具格；入夜後使用它可以召喚蝕日者（第 5 步）。瑟菈在打倒龍和撿到晨光之心時各有一段日誌。
- **重畫。** 龍的身體、頭和脖子用和怪物同樣的方式重新上色：暗紫的身體，邊緣留著一圈晨光的金色。
- 測試：戰場的魔王測試涵蓋降落、遠近不同的招式、硬皮、被觸發的招式排隊、冰凍與融冰、火焰燒傷、振翅吹開主角並吹熄火焰、倒下的時間，以及天亮時離場。

已在瀏覽器實際打過一場：降落後主角上前攻擊，火球、振翅、冰息、烈焰依序觸發並造成預期的效果，打倒後掉出晨光之心，主角撿起，血條和盤面恢復原狀。

### 第 5 步：蝕日者與結局

- **魔王的招式通用化。** 原本「方塊觸發龍的哪一招」改成「方塊觸發哪個魔王的哪一招」（`provokes`），另外資源可以直接傷害某個魔王（`wounds`，燈火傷害蝕日者）。招式多了召喚怪物、綁住方塊、先打結界三種效果；魔王可以高掛空中（主角打不到），也可以讓夜晚停下來。
- **蝕日者。** 資料寫在 `bosses.ts`：高掛天空、在場時夜晚不前進，只有燈火能傷害它，其他方塊觸發影雨、蝕光和日蝕。畫面在 `src/app/eclipseview.js`：天空中央一顆被金色日冕環繞的黑太陽，凝視時射出黑光，被燈火刺穿時發亮，倒下時放大、褪去。蝕之眷屬和其他怪物一樣是資料加剪影上色的圖。
- **晨光之心不會白白用掉。** 白天使用會退回；主角倒下、或天在蝕日者倒下前亮了，晨光之心都會回到主角手上。
- **結局。** 蝕日者倒下後，`StoryGraphics.showEnding` 用開場故事的方式播放五頁結局，接著顯示原本的通關畫面（統計、繼續、新遊戲＋）。統計多了「擊敗蝕日者」。
- 測試涵蓋方塊觸發與傷害魔王的規則、蝕日者高掛空中、召喚、綁方塊和先打結界。

已在瀏覽器實際打過一場：白天使用晨光之心會退回，入夜後蝕日者出現、盤面重洗並出現大量燈火；燈火造成傷害，麥穗、布匹、陶土分別觸發影雨、日蝕和蝕光；打倒後播放結局，通關畫面的新遊戲＋可以正常開始第二輪。

### 第三階段的結果

- 內容（資源、建築、道具、法術、暮光技、怪物、魔王、出現規則）都是資料，載入時檢查。
- 即時的移動與戰鬥都在 `src/core/field.ts`，有單元測試和單挑報表；原本的 13 個怪物類別、所有動作類別和龍的動作都已刪除。
- 怪物重新上色並改名，新增影魅、燈蛾、暮鴉、蝕之眷屬，墮落晨龍成為中魔王，蝕日者是最終魔王，遊戲有了結局。
- 晚綁定的參照剩 7 組：第 4 步拿掉了 WorldEntity 的一組，第 5 步為了讓蝕日者在場時盤面出現燈火，盤面多了一組查詢世界。其餘是實體透過 Graphics 繪圖、模組回頭詢問 Engine、寶物畫面查詢世界，要等第五階段重寫畫面才會消失。

### 第 1 步：黃昏抉擇與暮光技配置

- **規則在核心，資料在內容。** `src/core/blessings.ts` 定義恩賜與代價的種類（入夜時補滿某樣東西、夜晚長短、怪物生命與傷害、怪物數量、經驗倍率、不出現額外的怪物），把一個祝福換算成今晚的修正值，並依天數、這一局的種子和村子的進度挑出三個選項。九種祝福寫在 `src/content/blessings.ts`，載入時檢查。

- 測試涵蓋修正值的合併、選項固定且三個一組、出現條件，以及每種祝福都有中英文名稱。在瀏覽器實際選過祝福、婉拒、選暮光技，並確認入夜生效、天亮清除。

### 第 2 步：夜晚導演

- `src/core/night.ts` 的 `readOmen` 依天數、這一局的種子、主角等級與前一晚是否倒下挑出今晚的預兆；主角強度是「等級減去天數該有的等級」。預兆的效果和祝福用同一套效果類型（`Boon`），多了掉寶倍率、入夜時來的怪物、較短的連鎖也招來影魅三種。六種預兆寫在 `src/content/omens.ts`，和祝福一起在載入時檢查。
- 黃昏面板最上方顯示預兆和瑟菈的話，效果文字同樣由數值產生；狀態列的標記同時顯示預兆和祝福。今晚的修正值是祝福加上預兆。
- 存檔多了 `lastFallDay`：主角倒下的那一天，重來時的夜晚一定是寧靜之夜。
- 測試涵蓋倒下後的寧靜之夜、同一天固定、天數門檻，以及強的主角更常遇到困難的預兆。在瀏覽器確認過「鴉群」的預兆入夜時多來 3 隻暮鴉。

### 第 3 步：劇情引擎、日誌與圖鑑

- **引擎在核心。** `src/core/story.ts`：章節由事件觸發，條件有事件的參數（等於或至少）、天數、等級、遊戲計數和劇情旗標；選項會寫入旗標，回答可以接著幾句回應。每章每局只講一次。
- **劇情是資料。** `src/content/story.ts` 列出角色（和頭像在圖上的位置）與全部章節。原本寫在 `story.js` 裡的 52 段日誌都搬成章節，代號不變，所以舊存檔記得哪些講過。台詞的文字在語系檔的 `STORY`（新台詞）和 `JOURNAL`（舊日誌）。
- **對話框。** 對話框多了頭像（`tools/art/portraits.py` 畫的 `portraits.png`）和說話者的名字；有選項時遊戲暫停，選完才繼續。
- **記錄。** 選單多了「記錄」：守暮日誌依講述的順序列出全部章節（舊存檔沒有順序的列在「更早以前」），怪物圖鑑列出遇過的怪物和魔王，附圖、生命、傷害和瑟菈的介紹，沒遇過的只顯示「？？？」。打開時遊戲暫停。
- 存檔多了 `storyFlags`（選擇）和 `storyLog`（講述的順序與天數），主角倒下時也會保留。
- 測試涵蓋條件、只講一次、選擇記成旗標，以及每句台詞都有中英文文字、每個角色都有名字與頭像。在瀏覽器實際走過旅人的章節、打開日誌和圖鑑。

### 第 4 步：選擇的後果與建造選擇

- **選項可以改變今晚。** 劇情的選項多了 `tonight`：一串和祝福相同的效果，加進今晚的修正值，天亮清除。
- **長期的後果是資料。** `src/content/story.ts` 的 `CONSEQUENCES` 依旗標列出整局有效的效果（每晚入夜時劍的力道、結界上限、魔王的生命），`src/core/story.ts` 的 `consequences` 算出目前生效的效果，世界與遊戲狀態在對應的地方套用。
- **新章節。** 旅人的後續（留下或離開各一段），以及第 10 天起選完黃昏祝福後出現的蝕教使者交易。
- **暫停改成計數。** 黃昏面板、對話選項、記錄和建造計畫可能同時出現，每個都會 `hold` 一次，全部 `letGo` 之後才恢復；自動暫停的「點一下繼續」在還有選擇沒做完時不會恢復遊戲。重新開始時計數歸零。
- **建造計畫。** `src/app/plan.js`：早上出現新的可蓋建築、而且有兩棟以上可選時詢問先蓋哪一棟，選擇沿用原本「點建築設為優先」的機制。存檔記住問過哪些建築（`plannedSeen`）。語系檔加上建築與資源的名稱。
- 測試涵蓋後果的推算、接受交易後的結界上限、每種建築都有名稱，以及每個章節的觸發事件都有被監聽（這次就是靠實測發現使者的章節沒有被觸發，才加上這個檢查）。在瀏覽器實際走過建造計畫和使者的交易。

### 第 5 步：多重結局與世界變化

- **結局由選擇決定。** 蝕日者倒下時觸發 `eclipseFalls`，劇情講述晨光之心的處置（`heartChoice`；接受過蝕教交易的話改講多一個選項的 `heartChoiceCult`），選項把旗標 `ending` 設成 `sky`、`valley` 或 `cult`。世界監聽 `storyChoice`，看到 `ending` 才播放 `STORY_ENDINGS` 裡對應的結局，最後進入通關畫面。
- **劇情引擎的兩個擴充。** 條件多了 `{ flag, not }`（旗標不是某個值，從沒設過也算）；章節可以標 `again`，每次事件發生都講，不只第一次，所以新遊戲＋也會再問晨光之心的處置。
- **選擇的回聲。** 做決定之前，收留過的旅人（或想起他的瑟菈）先說一句話；新遊戲＋開始時（`PRESTIGE` 至少 1 次），瑟菈依上一次的結局說一句話。
- **太陽被啃食。** `src/core/day.ts` 的 `sunBite` 依距離太陽上次完整的天數算出缺了多少（每天 2%，最多 80%）。存檔多了 `sunWholeOn`：天上與山谷的結局把它設成當天，蝕教的結局不動。`src/app/longnight.js` 在天亮時把缺口寫進太陽的 CSS 變數 `--bite`，缺口畫在 `.celestial:after`，只在白天顯示。
- **村莊的燈火。** 夜裡建築是透明的（沿用原作的樣式），所以燈火放在 `.world` 裡另一層 `.villageLights`：入夜、讀檔和建築完成時依蓋好的建築重新排好，只在夜裡顯示，閃爍的節奏彼此錯開。
- 測試涵蓋新的條件與重複講述、每次蝕日者倒下都會問、只有接受過交易才會出現「交給蝕教」、每個結局都有兩種語言的文字，以及太陽缺口的規則。在瀏覽器實際走過收留旅人並接受交易後的三選一、山谷結局、新遊戲＋開始時的回聲，也確認蝕教結局不會讓太陽恢復。

### 第 6 步：重新平衡

**整晚的模擬。** `src/core/simulate.ts` 多了 `simulateNight`：用盤面和戰場的規則跑完一整晚。夜裡收集的方塊招來怪物或替主角補劍、補盾，燈火讓天亮更近並引來燈蛾，長連鎖招來影魅，入夜時暮鴉和預兆帶來的怪物出現；夜晚要打倒的怪物和點亮的燈火夠多才會天亮。模擬的玩家會等主角清完場上的怪再下一步，並預想每一步大概會連鎖成什麼樣子：劍或盾快用完時先補，一次只招少數幾隻怪，有燈火就點。主角從結界補滿、沒有劍和盾開始，而且一定會撐到天亮，所以能算出一整晚總共會受多少傷，就算那其實會讓主角倒下也一樣。

**限制。** 法術、道具和暮光技都沒有模擬，所以絕對數字偏高：平常的一晚，總傷害從第 2 晚的主角生命 1.5 倍左右，到第 25 晚的 3 倍左右。實際玩的時候，這些差距要靠法術和技能補上。後期的夜晚相對更吃力，這是原作的怪物數值，這一步沒有改動。模擬拿來比較同一晚的不同選擇，同一個種子在每種選擇下玩的是同一批夜晚。

**發現的問題。** 用 80 晚的平均比較每種祝福和平常的一晚：

- 「怪物生命提高」的代價非常重：每隻怪多撐幾下，同時圍上來的怪就更多。勇氣（怪物生命 +50%）在第 8 晚讓總傷害多了 284%，換來經驗 ×2；利刃（+25%）多了 139%，恩賜只是入夜時劍是滿的。
- 「怪物數量 ×2」一樣重：全副武裝多了 500% 以上，晨星雖然夜晚少 5 步，總傷害還是多了 100% 左右，經驗卻少了三成多。
- 夜晚多一步的代價比較輕，也容易預料：總傷害大約多主角生命的 13～36%（越後期越多），經驗多 7～9%。
- 結界在黃昏幾乎一定會補滿，所以護身燈火其實沒有作用。
- 靜夜在後期反而更危險：暮鴉、燈蛾和影魅是好打的怪，打倒它們也會讓天亮更近。少了它們，天亮要靠招來的強怪，第 16 晚的總傷害反而多了 61%。
- 蝕教的交易一面倒：接受的當晚總傷害少 90%（第 16 晚），往後每晚只因結界上限 −5 多 5%；拒絕的當晚卻多了 255%。
- 預兆裡的無月之夜（怪物每擊多 1 點傷害）讓總傷害多了兩倍以上，濃霧（怪物生命 +20%）多了一倍左右。

**調整。** 原則是代價和恩賜要相稱：補滿一樣東西，夜晚就多一步；怪物變強只當成最大恩賜的代價。調整後和平常的一晚相比（80 晚的平均，「傷害」是一整晚總傷害的變化，以主角生命的百分比表示）：

| 祝福 | 調整前 → 調整後 | 第 8 晚：傷害／經驗 | 第 16 晚：傷害／經驗 |
|---|---|---|---|
| 護身燈火 | 結界補滿 → 再加夜晚少 1 步 | −13%／−7% | −21%／−7% |
| 瑟菈的禱告 | 夜晚多 3 步 → 多 1 步 | +16%／+7% | +29%／+9% |
| 堅盾 | 夜晚多 2 步 → 多 1 步 | +15%／+7% | +18%／+9% |
| 利刃 | 怪物生命 +25% → 夜晚多 1 步 | +7%／+7% | +5%／+10% |
| 暮光湧泉 | 怪物每擊 +1 → 夜晚多 2 步 | +37%／+14% | +56%／+17% |
| 靜夜 | 再加夜晚少 5 步 | −93%／−63% | −61%／−52% |
| 勇氣 | 怪物生命 +50% → +20% | +136%／+100% | +95%／+99% |
| 晨星 | 怪物數量 ×2 → 怪物生命 +15% | −26%／−36% | −72%／−40% |
| 全副武裝 | 怪物數量 ×2、生命 +25% → 夜晚多 3 步 | +9%／+21% | +14%／+26% |

瑟菈的禱告補的是生命，模擬的主角入夜時生命是滿的，所以只看得到代價；暮光湧泉補的暮光槽（一次暮光技）也沒有模擬。兩者的代價都定得比其他補滿更輕或相當。

預兆：濃霧改成怪物生命 +10%、經驗 ×1.3（第 8 晚傷害 +27%、經驗 +30%）；鴉群改成多來 2 隻暮鴉；無月之夜拿掉每擊 +1 的傷害，只剩夜晚多 3 步、經驗 ×1.5（第 8 晚傷害 +53%、經驗 +83%），瑟菈的台詞也跟著改。影潮和流星雨不變。

蝕教的交易：接受的當晚改成「影魅、燈蛾和暮鴉不出現、夜晚少 5 步」（第 16 晚傷害 −61%），往後的代價加重為結界上限 −10（每晚約 +12%），蝕日者生命 +25% 不變；拒絕改成今晚多來一個蝕教術士（第 16 晚 +110%）。當晚兩邊的差距大約等於往後十幾晚累積的代價，越早接受越不划算，而且接受過就會開啟最壞的結局。

`tests/simulation.test.ts` 的整晚快照記錄四個階段（第 2、8、16、25 晚）每種祝福、預兆和蝕教交易的總傷害與經驗（24 晚的平均），之後改動任何數值，都能從快照看出它對夜晚的影響。

**沒有調整的地方。**

- 收留旅人只有好處：每晚入夜時劍有一半的力道，總傷害少 1～29%，拒絕他則沒有任何效果。台詞說「多一張嘴」，但遊戲裡沒有對應的代價。已決定維持現狀，不加代價。
- 原作的怪物數值和夜晚長度沒有改動。

### 第四階段的結果

- 六步全部完成：黃昏抉擇與暮光技配置、夜晚導演與預兆、劇情引擎（對話、頭像、日誌、圖鑑）、選擇的後果與建造計畫、三種結局與世界變化，以及依整晚模擬的重新平衡。
- 新的存檔欄位（選擇、講述順序、問過的建築、太陽上次完整的日子等）都有預設值，舊存檔直接讀取，不需要升級程式。
- 目標裡的「夜晚導演參考劇情進度」沒有做：預兆目前只看天數、這一局的種子、主角等級和前一晚是否倒下。要不要加，留給之後決定。
- 「精靈圖座標由美術工具輸出的清單產生」原本列在內容資料化的目標裡，但沒有排進第三階段的任何一步，移到第五階段第 1 步。

## 第五階段：畫面與體驗

### 方向

- **畫面照規則回傳的事件播放。** 盤面和戰場的規則都已經在 `src/core/`，畫面層只要讀狀態和事件來畫，不再自己決定任何規則。
- **場景和盤面改用 canvas。** 新的繪製程式放在 `src/render/`，用 TypeScript 寫；選單、狀態列和對話框維持 HTML，改寫後放在 `src/ui/`。

- **一次換一塊。** 每一步換掉一部分畫面，換下來的 jQuery 和 CSS 一起刪掉；每一步都能玩，也都會部署。

### 第 1 步：精靈圖清單

- **美術工具輸出清單。** `tools/art/build.py` 畫完圖檔後寫出 `src/content/sprites.json`：每張精靈圖在哪張圖檔、第一格的位置、每格的大小、橫向有幾格（動畫影格）、縱向有幾列（動作，或建築的等級）。目前有 53 筆：建築、怪物、主角（白天與夜晚）、墮落晨龍的身體、頭和脖子、日月、星星、暮晶碎片、寶箱、冰與火的特效、對話頭像，以及每種方塊白天、夜晚和巨龍戰的圖。
- **程式從清單取用。** `src/content/sprites.ts` 匯入清單；`graphics/sprites.js` 不再自己寫一份座標表，改從清單查位置，預先載入的圖檔也照清單。原本座標表上的介面圖示（愛心、道具、法術、選單等）其實都由 CSS 定位，程式從沒查過，所以沒有放進清單，留到第 5 步改寫介面時再由清單產生 CSS。
- **載入時檢查。** 每張精靈圖都要在它的圖檔範圍內，怪物資料的寬高要和精靈圖一致，建築和怪物用到的精靈圖都要存在。測試另外比對清單記的圖檔大小和實際 PNG 的檔頭，確定清單沒有過時。
- 重新建圖後所有圖檔一個位元組都沒變，畫面和之前完全一樣。原本的座標表有兩筆和圖檔對不上（夜間方塊寫成 468、龍的脖子寫成 1670，實際是 467 和 1700），都是程式沒用到的名稱，所以畫面不受影響；清單照實際位置記錄。

### 第 2 步：盤面改用 canvas

- **畫面元件。** `src/render/board.ts` 的 `BoardView` 在 canvas 上畫盤面。遊戲只告訴它每塊方塊發生了什麼：放在哪一格、等多久後滑到哪一格、淡出、多了或少了特殊效果；它照時間算出每塊方塊現在畫在哪裡。它不知道任何規則，也不靠計時器，每一格都由目前的時間算出來，所以分頁被藏起來再回來時，動畫會直接跳到該在的位置。
- **畫的內容和原本一樣。** 方塊照精靈圖清單取圖，依等級選列；白天、夜晚各有底色，外框用頁面的暖色，入夜和天亮時方塊翻面（半秒），外框顏色慢慢轉換；墮落晨龍在場時麥穗、陶土和布匹換成巨龍戰的夜間圖。燈籠方塊的橘色光圈、日輪方塊的金色光暈、影縛的斜紋、炸藥桶的紅光和爆炸的紅圈都改在 canvas 上畫，選取的方塊蓋上原本的選取框。從盤面上方落下的方塊只在盤面裡看得到。高解析度螢幕依像素比放大畫布，手機直式版面的格子較大（每格 70、方塊放大 1.15 倍）。
- **銜接。** `graphics/gameboard.js` 把盤面的繪製要求（清空、填滿、交換、消除）換成 `BoardView` 的動作，等待時間和原本完全相同，其餘模組不用改。方塊的等級和巨龍戰仍由盤面元素上的 class 決定（例如 `grain3`、`dragonFight`），畫面元件每一格讀一次；換等級時那一種方塊淡出、換圖、再淡入。
- **輸入。** 引擎改成讀 canvas 上被點到的是哪一格（`{ row, column }`），不再從方塊元素取資料；縮放過的版面也照實際大小換算。
- **刪掉的東西。** 方塊實體（`entity/tile.js`）和每塊方塊的 HTML 元素都拿掉了，CSS 少了約 470 行（每種方塊每個等級白天與夜晚的位置、翻面、特殊效果）。飛出盤面的資源圖示、燈籠與日輪的閃光、連鎖和豐收的提示仍是 HTML，疊在盤面上。
- 測試涵蓋方塊在路上的位置、淡出後被遺忘、翻面的時間與方向、依白天夜晚、等級與巨龍戰選圖，以及點到的格子。在瀏覽器實際交換方塊、看完一整串連鎖並比對畫面上的 64 格和盤面資料一致，也逐點檢查了底色、外框、特殊效果、爆炸、夜晚翻面，以及手機直式版面。瀏覽器主控台可以用 `boardView()` 取得畫面元件。

### 第 3 步：場景改用 canvas

場景裡的東西很多，分成四小步，每一小步都能玩、也都會部署：

| 小步 | 內容 | 狀態 |
|---|---|---|
| 3-1 | 天空與遠景：天空的顏色、星空、黃昏霞光、日月與太陽的缺口、遠山、村莊燈火 | 完成 |
| 3-2 | 建築：升起與沉下、等級、優先標記、材料進度 | 完成 |
| 3-3 | 主角、怪物、寶箱、投射物與特效 | 完成 |
| 3-4 | 墮落晨龍與蝕日者 | 移到第 4 步 |

**3-1 天空與遠景。** `src/render/sky.ts` 的 `SkyView` 畫在 `.world` 最底層的 canvas 上，依序畫天空的底色與往地平線的漸層、夜裡的星空、黃昏的霞光、太陽或月亮（白天時畫上蝕日者啃掉的缺口）、遠山，以及夜裡每棟建築的燈火。日夜和黃昏都照頁面上的 class 淡入淡出（1.4 秒），原本只有底色會漸變，星空和漸層是一下子切換的。遠山在夜裡改用預先畫好的暗色版本，不依賴各瀏覽器支援度不一的濾鏡。日月不再是 HTML 元素：`entity/celestial.js` 只記住位置和影格，`Graphics.moveCelestial` 和日夜交替時的落下、升起改成告訴天空目標位置和時間。太陽的缺口只在太陽那一面畫，所以不再需要 CSS 那段「等太陽落下再隱藏」的延遲。遠山和星空也加進了精靈圖清單。CSS 刪掉了天空、遠山、霞光、日月、缺口和村莊燈火的規則。測試涵蓋日月的移動、缺口只在太陽上，以及日夜與黃昏的淡入淡出；在瀏覽器逐點檢查了白天、黃昏、夜晚的天空、遠山、太陽的缺口、月亮和村莊燈火。

**3-2 建築。** `src/render/village.ts` 的 `VillageView` 畫在天空前面的另一塊 canvas 上（和原本的建築一樣在 z-index 1，怪物和寶箱仍在建築後面、主角在前面）。每棟建築依等級取圖；還沒蓋的建築在地底，主角開始敲打時用 5 秒升起；升級在收材料時，原本的建築抬高 20px，可以點它把升級設為優先；升級升起時原本的建築用 2.5 秒沉下去；夜裡建築淡出。材料送到一部分後，進度條從地面浮出，每種材料一條，顏色照方塊的等級（原本寫在 CSS 裡，例如木材 4～6 級是灰褐色）；建築升起時進度條沉進地面。被設為優先的建築上方有閃爍的星星。點擊改由畫面元件判斷點到的是哪棟建築的進度條，或哪棟為升級抬高的建築。建築實體不再有 HTML 元素：`Graphics` 的 `addBuilding`、`updateCosts`、`raiseBuilding`、`sinkBuilding` 等改成告訴畫面元件，原本用 jQuery 動畫做的升起改成計時器，夜裡中斷時一起取消。星星實體（`entity/star.js`）拿掉了。CSS 刪掉了建築、進度條，以及早就沒有程式在用的 `.blockPile`。左邊的材料堆和主角搬的積木仍是 HTML，第 3-3 步再改。測試涵蓋升起與落回、進度條的出現與沉下、升級時抬高可點和沉下、材料顏色；在瀏覽器實際送材料讓主角蓋好製磚坊，也用滑鼠事件點進度條把織布坊設為優先。

**3-3 主角、怪物、寶箱與投射物。** `src/render/actors.ts` 的 `ActorsView` 畫在建築前面的第三塊 canvas 上（z-index 10，和原本的主角一樣；不接收點擊，點擊會穿過去到建築）。戰場每跳一次（100 毫秒），`fieldview.js` 就把主角和每隻怪物的位置、動作列和影格告訴它，它在下一跳之前把人物滑到定位，一跳之內移得太遠就直接跳過去（例如影魅瞬移）。主角白天用白天的圖，入夜時夜晚的圖淡入蓋上；搬的積木畫在主角肩上，隨步伐上下晃，顏色照方塊等級。怪物各自有白色血條，倒下時血條淡出，屍體留 5 秒再淡出；飛行的怪物離地 24px，瞬移時淡出淡入。寶箱只在夜裡看得到，打開後換成打開的圖。箭和火球用一秒畫出一道弧線，先升後降，箭身隨之傾斜（火球也加進了精靈圖清單）。主角、怪物和寶箱都不再有 HTML 元素：主角的 `el()`、怪物的血條元素、寶箱實體和投射物實體都拿掉了，寶箱改成只記位置和戰利品的物件；`Graphics` 的 `addMonster`、`fireArrow` 刪掉，撿起積木時把積木元素從材料堆拿下來就好。CSS 刪掉了主角、積木框、血條、每種怪物的尺寸與血條位置、寶箱和投射物，共約 300 行。材料堆、戰利品圖示、升級光束、炸彈爆炸和魔王血條仍是 HTML。測試涵蓋主角滑動與跳躍、倒下的血條與屍體、瞬移的淡出淡入、箭的弧線與傾斜，以及天亮清場；在瀏覽器實際看主角搬積木、入夜後打倒殭屍、骷髏放箭、主角走去打開寶箱。

**3-4 移到第 4 步。** 兩個魔王的畫面幾乎都是特效：墮落晨龍的火球、冰息與火焰光束、地上的火、逐節爆開，蝕日者的黑光、影雨和碎裂，現在都各自用 CSS 動畫做。第 4 步要建的特效層（閃光、粒子、畫面震動）正好是它們需要的，所以先建特效層，再把兩個魔王連同特效一起搬過去，不必把同一批特效寫兩次。

### 第 4 步：光影與特效

|---|---|---|
| 4-1 | 特效層與畫面震動：燈籠與日輪的閃光、升級的光柱、炸彈的爆圈、寶箱的戰利品、爆炸與長連鎖時盤面晃動 | 完成 |
| 4-2 | 粒子：消除方塊、打擊、怪物倒下、建築完成 | 完成 |
| 4-3 | 提燈光照：夜裡的黑暗與光源 | 完成 |

| 4-5 | 蝕日者改用 canvas，特效改用特效層 | 完成 |
| 4-6 | 墮落晨龍改用 canvas，特效改用特效層 | 完成 |

**4-1 特效層與畫面震動。** `src/render/effects.ts` 的 `EffectsView` 畫在盤面元素裡另一塊 canvas 上，從世界的頂端一路蓋到盤面底部（z-index 3，不接收點擊），所以同一層能畫世界和盤面上的特效。目前有：燈籠方塊爆開時沿那一排和那一列的光帶、日輪方塊讓整個盤面亮起、升級時從天而降再向兩旁散開的光柱、炸彈在主角周圍炸開的白圈（只在世界裡）、寶箱打開時浮現的戰利品圖示（最後 0.3 秒往上飄並淡出）。每個特效照自己的時間播完就被移除。畫面震動也在這裡：`shake(力道, 時間)` 一開始最強、逐漸減弱，用 CSS 的 `translate` 移動整個盤面元素（世界、盤面和狀態列一起晃），不會和墮落晨龍來時讓盤面傾斜的 `transform` 互相干擾；較強的震動會蓋過較弱的。會晃的時候：炸藥桶爆炸、使用炸彈、燈籠與日輪方塊爆開、連鎖到第 8 波（快轉時不晃）、主角一次挨 5 點以上的傷害。道具圖示的排列順序改由美術工具寫進精靈圖清單（每格的名稱），程式照名稱找圖。原本這些效果是 HTML 元素加 CSS 動畫，現在全部刪掉了。測試涵蓋特效的時間與移除、震動的減弱與歸位、強弱震動的取代，以及道具圖示的名稱；在瀏覽器逐點檢查了光帶、光柱、戰利品、爆圈和震動。

**4-2 粒子。** 特效層多了粒子：每顆粒子記住出發的位置和時間、速度、重力和壽命，現在的位置直接由經過的時間算出來，不必每一格累加，也方便測試；同時最多 400 顆，超過時最舊的先消失。用在：消除方塊時從格子中心噴出那種材料顏色的碎屑（顏色和材料進度條相同，隨方塊等級改變；快轉的連鎖少噴一點）、主角打中時前方的火花、怪物倒下時冒出的一縷黑煙、建築蓋好時沿著地基揚起的塵土。測試涵蓋粒子的飛行、落下、淡出與數量上限，以及碎屑從格子中心出發；在瀏覽器實際交換方塊看到麥穗和石材的碎屑，也觸發了火花、黑煙和塵土。

**4-3 提燈光照。** 入夜後，特效層在世界的地面一帶畫上黑暗：從天空四分之一高度往下漸深，貼近地面最暗（不透明度 0.62），天空和月亮不受影響。主角的提燈照亮身邊一圈（半徑約 72px，微微閃動，中心有一點暖光），村裡每扇亮著的窗戶照亮一小圈；從黑暗中走近的怪物要進到光裡才看得清楚。黑暗先畫在另一塊畫布上，用 `destination-out` 挖出光圈再疊上去，不會擦掉同一層的其他特效。主角的位置和窗戶的位置由世界模組提供；特效層比世界先建立，所以取位置時不會順手建立世界。測試涵蓋夜色的淡入、窗戶和提燈的光源，以及提燈閃動的範圍；在瀏覽器比對了白天、夜裡遠處地面、主角身邊、窗戶旁和天空的明暗。

**4-4 多層遠景。** 美術工具多畫了兩樣：遠山腳下更低、更暗的近丘，稜線上有幾棵冷杉（和遠山一樣用正弦波疊出稜線，週期整除寬度，所以左右無縫）；以及三朵雲，底部帶陰影。天空現在依序畫：天空、星空、黃昏霞光、日月、雲、遠山、近丘、村莊燈火，所以雲會飄過太陽前面，太陽仍落在山後。四朵雲各自以不同速度往右飄，飄出畫面後從左邊回來；位置越高、越遠的雲飄得越慢，看得出遠近。夜裡雲淡到三成五，近丘和遠山一樣換成預先畫好的暗色版本。世界的畫面不會捲動，所以遠山和近丘本身不移動，只有雲在動。測試涵蓋雲的飄動、繞回和遠近的速度差；在瀏覽器確認了雲、白天與夜晚的近丘。

**4-5 蝕日者。** 兩個魔王分開做，先做比較單純的蝕日者。`src/render/eclipse.ts` 的 `EclipseView` 畫它的本體：黑色圓盤，外圍一圈被它偷走的金光，光暈每 3 秒一呼一吸。它畫在角色畫布的最底層，在村子的建築前面、主角和怪物後面，和原本的 HTML 元素一樣；建築的圖有 80px 高，畫在天空裡會被擋住半個。出現時從三成大小長到原尺寸（0.6 秒），1.5 秒內淡入。凝視和閃耀時變亮，蝕日時變暗、褪色，被燈火刺中時更亮並縮一下。每種狀態都用 0.3 秒漸入漸出，後來的狀態疊在先前的上面，所以被刺中之後會回到原本的暗色。碎裂時，它在 3.5 秒內脹大到 2.4 倍，越來越亮，然後消失。原本的亮暗用 CSS 濾鏡做，但 canvas 的 `filter` 不是每個瀏覽器都支援，所以改成直接調整漸層顏色的亮度和飽和度。

它的攻擊交給特效層，畫在建築和角色前面，夜裡也不會被黑暗蓋住：凝視落在主角身上的黑光、燈火從盤面射穿它的光束，以及影雨時從它下方落下的六滴影子。光束沿兩點畫線，各有自己的時間、顏色和光暈；光暈依像素比放大，高解析度螢幕上不會變細。`eclipseview.js` 只把戰場事件轉成這些動作。CSS 刪掉了蝕日者、兩種光束和影滴的規則，共約 80 行。

測試涵蓋出現、狀態的漸入漸出與疊加、碎裂，以及特效層的光束和影滴各自照時間結束。在瀏覽器逐點檢查了本體的黑盤、金環和光暈，以及黑光、燈火光束和影滴；也確認了碎裂後天亮、移除後畫面清空。

**4-6 墮落晨龍。** `src/render/dragon.ts` 的 `DragonView` 畫整隻龍。身體照動作列和影格取圖：站著、飛行、降落，以及振翅的前後兩半。三節脖子和頭用矩陣一節接一節算出位置：每節繞自己的中心轉動，再沿轉過的方向推出去，和原本 CSS 的巢狀 `transform` 相同。在瀏覽器把舊的 HTML 結構重建出來逐節比對，兩種面向、五種姿勢、兩種接點的誤差都是 0。姿勢之間用 ease-out 過渡，中途換姿勢時從目前的位置接著轉。原本用一張動態樣式表改所有關節的過渡時間，現在每個關節自己記住起點、終點和時間。嘴巴隨身體的影格一格一格開合，快的時候第一步跳兩格。面向右邊時用另一組圖（不是單純的鏡像），接點、轉向和頭的位置照原本 CSS 的規則換邊。

有幾處和原本不同。龍和其他怪物一樣畫在角色畫布上，在建築前面、主角後面；第 3-2 步之後，牠一直被建築的畫布擋在後面。瞄準時頭對著主角頭頂；第 3-3 步拿掉主角的 HTML 元素後，原本的算法量到的主角高度是 0，瞄的是地面。火球從嘴前直線飛到起火的地方；原本的飛行距離是用頭的高度算的，不一定剛好到。

冰息和火焰衝擊先在嘴前聚成一顆白球，0.75 秒後冰息拉成越來越細的長柱，火焰衝擊壓扁成一團飛向主角；這部分跟著頭一起畫。火球、地上的爆炸、逐節爆開和最後的大爆炸改由特效層畫：火球照飛行方向轉向，飛 0.3 秒；爆炸是由小變大、逐漸透明的白圈，只畫在世界範圍內。落地吼叫時，盤面原本用 CSS 動畫左右晃，現在改用特效層的畫面震動。

地上的火和包住主角的冰塊原本是一個個 `WorldEffect` 實體，現在由 `fieldview.js` 每跳照戰場的狀態告訴角色畫布。火畫在怪物和主角後面，冰塊蓋在主角前面；舊版的冰塊被主角的畫布擋在後面。`WorldEffect`、龍的 HTML 元素和動態樣式表都拿掉了。CSS 刪掉了龍、火球、光束、爆炸、盤面晃動，以及已經沒有元素在用的 `.monster` 和 `.worldEffect`，共約 440 行。

測試涵蓋降落、姿勢的過渡與中途換姿勢、面向右邊的翻轉、頭對準主角、嘴巴開合、吐息的形狀，以及從頭開始逐節爆開；特效層補上爆炸白圈和火球的時間。在瀏覽器實際叫出龍，看牠飛下來、落地、盤面傾斜和吼叫；主角被打倒、重來一天時，龍也正確移除。另外直接下指令出招，看了冰息、火焰衝擊、火球、爆炸和死亡的每個階段，也確認了地上的火和冰塊。

介面元件用 TypeScript 寫在 `src/ui/`。它們和 `src/render/` 一樣不直接讀遊戲的模組：文字、狀態和按下去要做的事都由呼叫的一方傳進來，所以可以在 jsdom 裡測試。`src/app/graphics/` 裡原本的模組只留下把遊戲事件轉給元件的部分。

晚綁定的參照目前有 10 組：第 3、4 步又多了日月和寶箱透過 Graphics 更新畫面，以及打擊的火花要查主角的位置。它們大多會隨著前幾小步消失，例如實體不再有 HTML 元素後就不需要 Graphics；剩下回頭詢問 Engine 和世界的幾組，在 5-7 改由引擎初始化時把需要的東西傳進去。

**5-1 介面圖示。** 美術工具把介面圖示寫進精靈圖清單：護盾和劍的量表（各九級，量表和外框各一列）、存檔欄位的按鈕、愛心（白天和夜晚的外框、大愛心的金框，以及裡面的紅色）、選單按鈕、音量圖示，以及法術和持續效果。`src/ui/icons.ts` 照清單產生一張樣式表，遊戲啟動時加進頁面。每條規則的選擇器和原本的 CSS 相同，圖檔和座標都從清單來：夜晚的版本是下一列，護盾和劍的等級是不同的影格，道具和法術照影格的名稱找。CSS 刪掉了這些手寫的座標，以及原作留下、早就沒有元素在用的分享按鈕、捐款按鈕和標誌，共約 470 行；`icons.png` 上這些舊圖也清掉了，檔案小了約 15%。

改的時候發現兩個問題。被冰息凍住時，法術按鈕旁的狀態欄顯示的是空白圖示：美術工具重畫圖示時清掉了這一格，卻沒有畫新的，現在補畫成雪花。存檔欄位的星星，原本的座標比圖高 1px，最底下一列被切掉；改照清單取位置後就完整了。

測試涵蓋照影格、列和名稱取位置，樣式表的圖檔與座標，護盾和劍的每個等級，每種道具、法術和持續效果都有圖示，以及座標都在圖檔範圍內。在瀏覽器把白天、夜晚和九個等級下的 482 個圖示元素，改動前後的背景圖、位置、重複方式、底色和大小逐一比對：除了星星的 1px，全部相同。

**5-2 材料堆與暮晶碎片。** 世界裡最後兩樣 HTML 改畫在建築的 canvas 上。左下角的材料堆照存貨畫：外框隨麥穗的等級，從三格見方長到五格寬、四格高（0.2 秒）；材料塊照原本頁面的排法，最底下一排從右往左放，還沒放滿的排靠左；每塊照裝了多少，從左邊填上材料的顏色，數量變了就在 0.3 秒內填滿或倒空。材料堆和建築一樣在夜裡淡出，第一次出現時淡入，蓋基地建築時暫時淡出。在瀏覽器把原本 HTML 的 57 種排法（四種大小，每種從一塊到放滿）和畫布算出的位置逐塊比對：外框和 469 塊材料的位置完全相同，填色寬度最多差 0.017px，是瀏覽器排版把寬度取到 1/64px 的差別。

暮晶碎片照找到的數量畫在塔的頂樓，隨時間上下浮動。原本碎片是 HTML 元素，在建築的畫布後面，而塔的頂樓畫得不透明，所以白天其實看不到，只有夜裡建築淡出後才露出來。現在畫在塔前面，白天看得到，夜裡也不會淡出。

實體不再有 HTML 元素：`Entity` 的 `el()` 和量元素大小的 `width()`、`height()`，材料塊和怪物的元素，以及碎片實體（`entity/gem.js`）和材料堆的畫面模組（`graphics/resources.js`）都拿掉了。`Graphics` 刪掉了替實體設定位置和精靈圖的函式，以及一個早就沒有呼叫者的移動動畫迴圈。日月改由世界在建立時告訴它怎麼更新天空，寶箱打開時直接告訴角色畫布，所以實體、日月和寶箱都不再需要晚綁定 Graphics，晚綁定的參照剩 7 組。CSS 刪掉了材料堆、材料塊和碎片，約 130 行。

測試涵蓋材料堆的排法、外框隨等級長大、淡入與暫時淡出、材料的填滿，以及碎片依數量選列和浮動。在瀏覽器實際收集材料，看主角把裝滿的木材和布匹搬走、其餘留在材料堆裡，也確認了夜裡材料堆淡出、碎片仍在。

**5-3 狀態列。** `src/ui/status.ts` 的 `StatusBar` 管盤面旁的狀態。愛心照最大生命分成幾顆，超過十四顆時前面的變成大愛心；生命從最後一顆往前填，新的愛心一顆接一顆跳出來。護盾和劍裝了東西才出現，用完就收起來。經驗條、黃昏的結界和今晚的徽章也在這裡，魔王的血條則在世界上方滑進滑出。`src/ui/notices.ts` 管天亮時的天數、黃昏、連鎖和豐收的提示，`src/ui/flights.ts` 管消除方塊時飛向材料堆、劍或世界兩側的小方塊。三個元件都用原生的 DOM，產生的 HTML 和 class 都和原本一樣，所以樣式表不用改。`graphics.js`、`blessings.js` 和盤面模組裡的這些 jQuery 都拿掉了，`dusk.js` 已完全不用 jQuery。

飛出去的資源方塊原本打算移到特效層，但它會飛到盤面左邊外面的劍，而特效層的畫布只有盤面那麼寬，畫上去會被切掉，所以仍是 HTML。

改寫時順手修了一個小地方：魔王的血量歸零後，血條一秒內就移除；魔王過幾秒消失、或天亮結束巨龍戰時再把血量設成 0，原本會再建一條馬上又收起來的空血條，現在沒有血條時就不建。

測試涵蓋愛心的數量與大愛心、從最後一顆往前填和一顆接一顆跳出，護盾的出現與收起，經驗條、結界、徽章，魔王血條的滑入與移除，天數、黃昏、連鎖與豐收提示的時間，以及資源方塊的起點、終點與重複使用。在瀏覽器實際觸發愛心、護盾、劍、結界、徽章、魔王血條、連鎖、豐收和黃昏，畫面和主控台都正常；資源方塊確認了 CSS 轉場照原本的 0.7 秒和曲線啟動。

**5-4 道具、法術與暮光技。** `src/ui/inventory.ts` 的道具欄、`src/ui/magic.ts` 的法術按鈕與持續效果、`src/ui/skills.ts` 的暮光技列，都改成 TypeScript 和原生 DOM，HTML 和 class 和原本一樣。按下按鈕的處理原本寫在引擎裡，靠 jQuery 的事件委派找出按到哪個按鈕；現在由各元件自己接住：道具欄送出按了哪個道具的事件，由引擎決定現在能不能用，法術按鈕自己開合選單、施放按到的法術。按下的事件和原本一樣不再往外傳，所以不會順便關掉選單，也不會觸發盤面的其他處理。炸彈的爆圈改照角色畫布上主角的位置畫，不再晚綁定世界，晚綁定的參照剩 6 組。

順手修了一個小問題：法術選單關上後 0.2 秒才把法術收起來；如果在這 0.2 秒內再打開，原本會把剛打開的選單裡的法術收掉，現在重新打開時會取消收起。

測試涵蓋道具欄淡入、每種道具的按鈕與數量、按下道具會使用且事件不往外傳；法術按鈕的魔力、全滿發光、開合與施法，魔力不足時打不開，淡出中不能施法，淡出中重新打開；持續效果的閃爍、重新開始與提前結束；暮光技列的技能、量表與施放。在瀏覽器實際按了補血藥水，打開法術選單施放加速，加速的圖示出現在旁邊；也確認了暮光技列和施放。
